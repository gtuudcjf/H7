# 20 kHz 改动与编码器 CRC 故障分析（2026-10-29）

首次诊断按软件回归方向对照 HEAD（原 10 kHz 实现）与当时工作区，只增加诊断程序。本轮用户授权后，已在接收层实施下述并发修复；保留用户的电流命令与 Keil 配置，未烧录。下面的“缺陷分析”和隔离副本表格记录的是修复前状态，末尾为本轮实施记录。

## 已有录屏证据

`20261029_135325.mp4` 中，运行期间 CRC 错误计数持续增加；停止后 `fault=0x0A`，对应 `MOTOR_FAULT_ENCODER_STALE`，`mode=5`、`run_state=6`，CRC 计数约 19418，SPI 错误、DMA 超时及保护区错误计数为 0。停机直接原因是有效角度过期保护，而非模式 3 的定时停止或速度目标限制。Watch 是异步刷新，不能把不同字段当作同一控制周期的同步记录。

新增 `20261029_141537.mp4` 时长约 39.25 s，可读的运行阶段始终为模式 3、`iq_ref_a=0`、`fault=0`，机械位置基本不变。约第 5 秒 CRC 为 `0x01`，约第 37 秒为 `0x29`（41），约 32 s 增加 40；SPI 错误、DMA 超时、保护区错误仍为零。这说明本次零 Iq 静止记录下 CRC 没有快速增长。画面未展示一个非零 Iq 转动区间；前次转动录像可供参考，但无法仅凭两段录像保证同一固件版本、速度和计时窗口，不能据此断言运动/电气干扰或并发问题是全部实机根因。

## 对照结果

| 项目 | 原实现 | 当前实现 |
|---|---|---|
| 快控制周期 | 100 μs | 50 μs |
| 编码器请求间隔（无忙碌/阻塞时） | 100 μs | 2 × 50 μs = 100 μs |
| SPI4 | 8 位、CPOL 高、第一边沿、分频 128 | 未改 |
| SPI4 时钟 | 标称 120 MHz / 128 = 0.9375 MHz | 未改 |
| 每帧 | 6 字节 / 48 个时钟，标称 51.2 μs | 未改 |
| 控制 / ADC 中断抢占优先级 | 0 / 0 | 未改 |
| SPI4 / DMA 中断抢占优先级 | 1 / 1 | 未改 |
| DMA 超时计数 | 严格 `>2`，第 3 tick | 严格 `>5`，第 6 tick |
| DMA 超时名义窗口 | 300 μs | 300 μs |
| 有效角度过期计数 | 严格 `>10`，第 11 tick | 严格 `>21`，第 22 tick |
| 有效角度过期名义窗口 | 1.1 ms | 1.1 ms |

因此，代码没有把编码器请求翻倍，也没有把过期/超时保护的名义时间减半。实际请求可能因 HAL_BUSY 或中断延迟而跳过，实际传输起点及间隔仍需测量。更高频率的高优先级中断改变了低优先级回调的执行条件；“保留 SPI 时钟和请求频率”不能单独证明通信不受影响。

## 接收缓冲区被过早释放：已复现的并发缺陷

`Core/Src/motor/biss_encoder.c` 的完成回调先写 `dma_busy=false`，随后才调用 `BissFrame_Parse17(encoder_rx.storage, &frame)`。`BissEncoder_StartRead()` 仅检查 `dma_busy`，不检查解析过程是否仍占用接收缓冲区。

SPI4 完成回调可被 TIM8/ADC 抢占。TIM8 每隔两个快周期尝试启动新 DMA。当前使用的本地 STM32CubeH7 v1.12.1 HAL 在 SPI EOT 处理关闭传输、设置 `HAL_SPI_STATE_READY` 后才调用用户完成回调，因此 HAL 的忙状态不能保护应用层的解析阶段。

允许出现的交错为：

1. 帧 A DMA 接收完成；完成回调清除 `dma_busy`，尚未完成解析。
2. TIM8 抢占，下一次 `StartRead()` 成功，DMA 再次使用同一接收缓冲区。
3. 回调被暂停期间，新 DMA 可以独立写入缓冲区。
4. 解析恢复时可能读到帧 A 的 CRC 和帧 B 的位置，或者一次解析内读到不同版本的数据。
5. CRC 不匹配，但 SPI 硬件传输本身成功，因此 SPI 错误和 DMA 超时计数可以保持零。

`biss_frame.c` 虽然复制了 `frame->raw`，后续位解析仍读取传入的 `raw`，这份诊断副本目前没有隔离实时 DMA 写入。

这是旧代码已经存在的缺陷。20 kHz 缩短了高优先级任务之间可留给接收回调的时间，可能使原先未出现的交错发生。尚未测量实机抢占时长，不能据此断言录屏中的全部 CRC 错误都由这个缺陷造成。

## 诊断复现结果

运行：`python .tools/check_encoder_preemption.py`。诊断使用真实帧解析器及接收实现，HAL 由主机桩模拟；两份完整的输入帧均先通过真实 CRC 校验。抢占用例模拟下一次 DMA 已开始写入新位置字节、尚未写入新 CRC 的时刻，不模拟电气噪声。

| 接收实现 | 无抢占 | 注入上述交错 |
|---|---|---|
| HEAD 的原接收实现 | 有效帧 1，CRC 错误 0 | 有效帧 0，CRC 错误 1 |
| 当前接收实现 | 有效帧 1，CRC 错误 0 | 有效帧 0，CRC 错误 1 |

上述原/当前版本的 SPI 错误及超时均为零。这里的原实现仅用于比较接收逻辑，不代表在主机上测量了真实 10 kHz 中断时序。隔离副本只验证所有权修正方向，不是完整可交付固件修复。

同时运行 `python tests/run_control_tests.py`，原有 37 项检查通过。原有测试覆盖正常传输、解析与超时边界，没有覆盖“完成回调解析时又启动下一次 DMA”的交错，不能证明实机中断时序正确。

原始诊断程序保存在被 Git 忽略的 `.tools/`。修复后该诊断命令更新为比较 HEAD 原接收实现与当前修复实现；正式回归测试位于 `tests/test_biss_concurrency.c`，不依赖 `.tools/` 中的诊断源文件。

## 快照发布还存在一致性隐患

完成回调逐项更新 `position_raw`、`sequence`、`valid_age_ticks`、`ready`。`GetSnapshot()` 复制时关闭中断，只能防止复制期间被修改，不能防止高优先级控制任务先抢占正在更新一半的低优先级发布者，再复制到一份新旧字段混合的快照。

这主要影响角度及新帧判断，不能单独解释 CRC 错误计数。修复缓冲区所有权时，应把最终快照发布一并做成短临界区；不要为了简单而将整个 CRC 解析过程都放入关中断区。

## 建议的修正与实机验证顺序

1. 引入独立的 `frame_processing`/缓冲区所有权状态，完成回调首先占有该状态，`StartRead()` 在 DMA 或解析占用期间返回 HAL_BUSY，直到所有成功/失败路径完成发布才释放。DMA 的硬件超时计数与解析占用分开，避免把解析时间误算成硬件传输超时。
2. 在局部变量完成解析，以短临界区统一提交快照和释放状态；处理初始化、错误、终止路径的复位。解析改读稳定副本只能作为补充，复制本身也必须受所有权保护。
3. 把诊断交错纳入正式回归测试，验证失败帧仍保留最后有效位置、解析阶段不会误触发 DMA 超时、错误路径不会永久 busy。
4. 保持 20 kHz/10 kHz、SPI 时钟、电流及保护设置一致，仅替换这一项并发修正进行实机对照，记录单位时间有效帧和 CRC 错误增量，以及最终故障码。
5. 用 DWT 或 GPIO 测量 TIM8、ADC 控制和 SPI 回调的最大执行/延迟时间；20 kHz 控制周期仅 50 μs，需要验证实际预算。观察请求有没有跳过以及有效角度的最大间隔。主机测试不能替代此项测量。

在取得这些结果前，不应通过提高过期门限或关闭 CRC 保护来掩盖问题，也不宜直接进入速度环来验证一个仍可能失去角度反馈的系统。

## 已实施修复与软件验证

- `biss_encoder.c` 增加 `frame_processing`，完成回调进入时在短临界区将 DMA 所有权交接给解析状态。`StartRead()` 原子检查/占有缓冲区，DMA 或解析占用时返回 HAL_BUSY。
- CRC 解析仍允许中断，解析期间只累积有效角度年龄，不累计硬件 DMA 超时；成功、CRC 失败、保护区损坏均在完成快照发布后释放所有权。
- 快照写入、SPI 错误与中止回调使用短临界区，与读取端配对，保持调用前 PRIMASK。
- StartRead 发现保护区损坏时清零连续有效帧计数，防止修复保护区后仅收一帧就提前恢复 ready。
- `biss_encoder.h` 的 busy/API 注释同步说明 DMA 和解析占用。频率、SPI 时钟/优先级、CRC 与超时门限不变，用户 `main.c` 的 0.7 A 给定保留。

测试先观察到原实现 ownership/publication 两项失败，修复后通过。保护区恢复计数另有一次独立 RED→GREEN。`python tests/run_control_tests.py`：24/48 V 各 18 套，含非法母线选择共 39 项通过。`python tests/test_host_compiler_cli.py`：2 项通过。测试还覆盖解析可抢占、解析期年龄维护、不误触发 DMA 超时、CRC 失败保留最后有效位置、TX/RX 保护区损坏恢复、HAL_ERROR/HAL_BUSY 启动返回、SPI 错误/中止、Abort_IT 失败、重新初始化及 PRIMASK 保持。

PowerShell 九项入口分别执行，六项通过；`test_motor_control_integration`、`test_encoder_mode_integration`、`test_speed_iq_07_trial` 三项失败，均因旧脚本要求 main 的编码器电流启动为零，而用户当前配置是 0.7 A。没有修改用户给定，也没有放宽这些断言。完整套件不能报告为全部通过。

最终源码分别通过 ARMCC 5.06 update 5 的 24 V 和 48 V Keil 构建，均为 0 错误、0 警告。默认工程不加母线覆盖宏，仍选择 24 V；48 V 通过被 Git 忽略的独立验证工程添加 `MOTOR_BUS_VOLTAGE_SELECT_V=48`，编译依赖记录也确认该定义存在。构建日志为 `MDK-ARM/biss-fix-24v.log` 和 `MDK-ARM/biss-fix-48v.log`。产物分别为 `MDK-ARM/emptytest/emptytest.axf` 与 `MDK-ARM/emptytest/bus48/emptytest48.axf`，未烧录。

独立审查未发现本轮新增缺陷。另有既有边界未纳入本轮：若 HAL SPI EOT 处理在调用用户回调前被控制 ISR 延迟至超过 DMA 超时，abort/旧完成回调交错仍需单独验证。本轮主机测试在用户解析入口注入抢占，不能覆盖这个 HAL 入口窗口。因此仍须检查实际 ISR 预算和实机结果。

## 修复后的实机对照

1. 重新编译匹配实际母线的固件；本轮默认仍为 24 V，未执行烧录。当前源码是用户设定的 0.7 A 启动，不能把它当成零 Iq 固件。
2. 在相同硬件、固件和采集设置下分别记录零 Iq 静止与既定电流转动的固定时长；每段记下起止时间、CRC 计数差、SPI/超时/保护区错误以及 mode、run_state、fault、encoder_age_ticks。各段之间仅改变 Iq，并从静止稳定后开始计时。
3. 重点查看 CRC 是否连续成串、有效角度是否出现长间断；累计少量 CRC 不能单独解释过期停机。若再次停止，保留现场故障字段及录屏，不先复位。
4. 用 DWT/GPIO 确认 50 μs 控制预算与 SPI 完成延迟。软件测试通过代表已复现的竞争条件得到修复，不代表实机停机问题已验收。
