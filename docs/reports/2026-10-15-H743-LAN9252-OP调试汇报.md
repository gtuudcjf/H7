# STM32H743 与 LAN9252 从零进入 OP 的调试总结

代码移植与实板联调阶段汇报

汇报对象  指导教师

整理日期  2026 年 10 月 15 日

## 阶段结论

我们已在自研 STM32H743 与 LAN9252 板卡上完成最小 EtherCAT 从站软件的移植和实板联调。TwinCAT 能识别实验设备、在线读取 CoE 对象，并使从站依次进入 PREOP、SAFEOP 和 OP。最终截图显示 Current State 与 Requested State 均为 OP，InfoData.State 为 8，WcState 为 0，CycleCounter 已达到 2127，ControlWord 保持 0，错误数为 0。

这次工作的主要成果，是打通了“PC 主站网口 → LAN9252 → SPI1 → H743 从站协议栈 → 周期输入数据”的完整通信链路。OP 已经在实板上实现，但不等于长期稳定性、1 ms 实时性能或电机 EtherCAT 控制已经验收。

从最初 MISO 无有效响应到最终进入 OP，问题分布在不同层次：板上 EEPROM 空白、H7 分段 SPI 传输的 IO 保持配置、HAL 毫秒 Tick 与微秒预算之间的边界问题，以及 TwinCAT 主站周期通信未启动。前期还完成了参考工程裁剪、SSC 移植、邮箱边界修正和电机隔离，不能把整个过程简单归结为某一根线或某一个寄存器。

# 1 系统组成与最小验证目标

### 1 1 硬件和开发环境

板卡使用 STM32H743 作为应用控制器，LAN9252 作为 EtherCAT 从站控制器。LAN9252 带以太网 PHY，连接外部串行 EEPROM、25 MHz 晶振和两个网络端口。PC 通过专用网线连接从站 IN 端口，H743 通过独立 SPI1 访问 LAN9252。

开发环境为 Windows、Keil MDK 工程 emptytest、ARMCC 5.06 update 5 和 STM32Cube H7 V1.12.1。主站使用 TwinCAT 3 XAE Shell，截图中 build 为 4024.65。当前笔记本网卡用于台架功能实验；不能由本次 OP 结果直接推导正式实时网卡兼容性。

| 信号 | H743 引脚 | 配置与用途 |
|---|---|---|
| CS | PA4 | GPIO 推挽，空闲高，软件控制片选 |
| SCK | PA5 | SPI1 AF5 |
| MISO | PA6 | SPI1 AF5，LAN9252 返回数据 |
| MOSI | PA7 | SPI1 AF5，H743 发送数据 |
| SYNC0 与 SYNC1 | PE0 与 PE1 | 普通输入，本阶段不启用同步中断 |
| IRQ | PE3 | 普通输入，本阶段轮询，不启用 EXTI |
| DRV enable | PC4 | 调试模式明确拉低，功率级禁用 |

### 1 2 为什么先做通信而不接入电机控制

原 H743 工程已经包含电机、编码器、ADC、PWM 和 VOFA 相关功能。如果在首次 EtherCAT 调试时同时启动这些功能，既会增加时序干扰，也可能把主站输出误当成电机指令。因此我们使用 ETHERCAT_BRINGUP_ONLY=1，将本阶段限制在通信验证。

该模式仅执行公共 MPU、HAL 和时钟初始化，随后初始化 GPIO、设置 PC4 低和 CS 高、启动 SPI1、调用一次 EtherCAT_Init，再在主循环持续调用 EtherCAT_Service。不启动电机初始化、校准、PWM、ADC 采样、编码器初始化或电机服务。

### 1 3 需要区分的两条访问路径

PC 通过 EtherCAT 网口可直接访问 LAN9252 的 ESC 寄存器；H743 则通过 SPI 访问同一芯片。前者可用，不等于后者已可用。早期 TwinCAT 读取寄存器 Working Counter 为 1，只能证明那次网络访问得到响应，不能证明 H743 已运行 SSC 或已经能推进 AL 状态机。

本阶段采用轮询 FreeRun，关闭 DC、AL Event IRQ 和 SYNC 中断，先减少同步和中断因素，再逐层证明 SPI、邮箱、状态机和 PDO 功能。

# 2 从参考工程到 H743 的移植结构

### 2 1 参考来源与裁剪原则

仓库中的 STM32F407 与 LAN9252 SPI 示例提供了 SSC 5.11 和 LAN9252 SPI 配置参考。我们没有把 F407 工程整包复制到 H743，而是保留需要的协议栈逻辑，将与平台、示例外设和应用语义有关的部分分离。原参考目录保持只读，原作者与版本声明保留在导入文件中。[L1]

导入的 SSC 核心为 ecatappl、ecatcoe、ecatslv、mailbox、objdef、sdoserv 和 coeappl 七个源文件。重新提供项目自己的 el9800hw.h 硬件接口，不引入 F407 的硬件驱动、示例 LED 或模拟量应用，也不在第一阶段加入 CiA402、FoE、EoE、SoE 等功能。

### 2 2 分层后每一层负责什么

| 层次 | 主要文件 | 责任 |
|---|---|---|
| H743 板级适配 | lan9252_board.c | HAL 收发、DWT 计时、CS 控制回调与 HAL 故障快照 |
| LAN9252 协议 | lan9252_spi.c | Direct、CSR、PRAM 访问，探测和访问预算 |
| SSC 硬件接口 | lan9252_port.c | HW_EscRead/Write、事件与计时接口、静态邮箱池、首错锁存 |
| SSC 核心 | EtherCAT_SSC/Src | AL 状态机、SM、邮箱、CoE、对象字典访问 |
| 最小应用 | ethercat_app.c 与 app_core.c | 固定 PDO、回环语义和安全复位 |
| 服务集成 | ethercat_service.c 与 main.c | 一次初始化、持续轮询、运行诊断和故障停服 |

这样划分后，可以用假 transport 测试协议帧，用受控 HAL 测试板级超时，用真实 SSC 源码测试邮箱与对象字典，也能在实板上把错误定位到具体层次。

### 2 3 H7 SPI 与访问方法

SPI1 使用主机全双工、8 位、MSB first、Mode 0、软件 NSS、无 NSS pulse。SPI123 内核频率按配置核对为 64 MHz，分频 16，得到 SCK 4 MHz。没有在首次调试中使用 DMA 或 SPI 中断。

Direct 访问用于 LAN9252 主机寄存器，公开接口限制为合法地址上的对齐 32 位访问；ESC 寄存器通过 CSR 间接访问，过程 RAM 通过 PRAM FIFO 访问。不能把 LAN9252 的全部地址都当成可直接 SPI 读取的 ESC 地址。

协议层负责完整事务的 CS 生命周期。快读命令包含命令、地址和 dummy byte，数据阶段继续在同一次 CS 低电平内完成。板级适配器可分块收发，但不得自行切换片选或重试掩盖上层错误。

# 3 实验身份与最小对象字典

### 3 1 固定一套实验设备描述

设备名称确定为 H743-LAN9252-LAB。固件身份集中在 ethercat_identity.h，主站描述使用独立的 H743-LAN9252-LAB.xml，不沿用参考板厂商、名称、LED 或模拟量对象。ESI 是电脑上的 XML 描述；SII 是板上 EEPROM 的二进制内容；SSC 对象字典是 H743 固件运行时提供的内容，三者需要逐项核对。[L2]

| 字段 | 固件与实验 ESI 目标值 |
|---|---|
| Vendor ID | 0x00F0C743，仅供本地实验，并非 ETG 分配 |
| Product Code | 0x00009252，十进制 37458 |
| Revision | 0x00000001 |
| Serial Number | 固件 0x1018 与 ESI 默认值为 1 |
| SII 目标有效大小 | 2048 字节 |
| 上电 PDI 类型 | 0x80，LAN9252 SPI 接口 |

### 3 2 用最小 PDO 区分状态进入与数据交换

RxPDO 和 TxPDO 的方向均从从站角度命名：RxPDO 是从站接收主站输出；TxPDO 是从站发送主站输入。本项目主站输出为 2 字节，主站输入为 6 字节。

| 对象或配置 | 类型与内容 | 映射 |
|---|---|---|
| 0x7000:01 | UINT16 ControlWord | RxPDO 0x1600 |
| 0x6000:01 | UINT16 StatusWord | TxPDO 0x1A00 第 1 项 |
| 0x6000:02 | UINT32 CycleCounter | TxPDO 0x1A00 第 2 项 |
| 0x1C12:01 | 0x1600 | SM2 分配 |
| 0x1C13:01 | 0x1A00 | SM3 分配 |

StatusWord 仅回显 ControlWord 的 bit0，其余位为 0。CycleCounter 在有效 OP 交换、收到有效输出后随 FreeRun 应用迭代递增；它不是硬件时间戳，也不保证一个主站周期正好加 1。两个字段都不控制电机。

### 3 3 固定 SM 布局

| SM | 起始地址 | 长度 | 用途与控制字节 |
|---|---|---|---|
| SM0 | 0x1000 | 128 字节 | 主站到从站邮箱，0x26 |
| SM1 | 0x1080 | 128 字节 | 从站到主站邮箱，0x22 |
| SM2 | 0x1100 | 2 字节 | RxPDO，0x64 |
| SM3 | 0x1400 | 6 字节 | TxPDO，0x20 |

对象在 MCU 内的自然对齐布局与线上 PDO 布局不是同一回事。代码显式按小端字节打包 2 字节输出和 6 字节输入，不直接 memcpy 整个可能带填充的 C 结构体，避免把内存 padding 作为过程数据发送。

# 4 移植期间发现并修正的软件问题

### 4 1 编译通过之前的对齐问题

真实 ARMCC 全量构建曾出现 7 个错误和 3 个警告，主要涉及 packed 邮箱结构成员的地址不能直接作为普通 uint16_t 指针使用，以及关闭功能残留的未使用函数。主机编译通过并不意味着目标编译器对 packed、指针和 ABI 的处理也相同。[L3]

处理时先保持线上字节布局不变，再明确邮箱缓冲区为 4 字节对齐，从经过验证的字节基址加偶数字节偏移构造字访问指针，同时增加大小、偏移和对齐检查。被关闭的分段 SDO 辅助函数按原功能宏排除，不通过屏蔽警告掩盖问题。真实目标编译、链接、map 和反汇编用于核对最终访问。

### 4 2 邮箱长度不能把总容量当成有效负载

128 字节 SM 邮箱包含 6 字节邮箱头，不能再允许 128 字节 payload。前期检查发现接收、发送和某些 SDOInfo 路径的长度加法、末字触发位置及记录名称长度处理存在边界风险。错误可能表现为越界访问、响应畸形或后续通信不稳定，而不是简单编译失败。[L4]

修正采用先减后比的容量检查，在拷贝、解析、分发和物理发送前都约束长度；同时检查 CoE、SDO、SDOInfo 子头，修正恰好填满和奇数长度情况下的末字节位置。超长响应转换为有界邮箱错误，取消相关续传状态，无法容纳错误包时释放请求而不继续 I/O。

### 4 3 缓冲区所有权和有限等待

参考源码虽然关闭 MAILBOX_QUEUE 宏，仍保留有限队列及重复响应生命周期。因此不能临时分配一块栈缓冲区并在下一轮重用。项目采用 24 个、每个 128 字节且 DWORD 对齐的静态块，保留跨服务调用的所有权；停止时排空队列，避免遗漏释放、别名重复释放和无内存分支的 double free。

SyncManager 使能与关闭确认循环也改为有界：受 1000 微秒与最多 64 次读取约束，访问错误立即锁存。计时使用单调微秒基线，每轮最多补处理 8 个 1 ms tick，并保留小数和积压量，避免无限追赶阻塞主循环。

### 4 4 功能声明必须与实际配置一致

参考生成代码存在宏关闭后仍宣告 SM/DC 能力、仍选择 SM 同步的情况。我们将能力声明和选择逻辑与 FreeRun、无 DC、无 AL Event 中断的真实配置一致，并对未支持的访问明确拒绝。对非法子索引、错误 SDO 长度和不支持的 Complete Access 先检查再访问对象。

这些问题来自移植与主机测试阶段，不能写成每一项都曾在实板导致 OP 失败。它们的意义是先排除已发现的软件边界风险，为后续硬件定位提供可信基础。

# 5 实板起点与空白 EEPROM 的处理

### 5 1 最初现象

最初已测量确认相关线路没有短路，但 MISO 没有有效返回波形。此时板上 EEPROM 尚未写入匹配配置，电脑也尚未安装实验 XML。TwinCAT 扫描到的设备显示产品和版本为 FFFFFFFF，EEPROM Hex Editor 可见连续 FF，说明设备描述和上电配置尚未准备好。

我们曾更换到同批贴装的另一块板。两块板设计一致，且 EEPROM 均为空白，所以换板可帮助排查个体贴装差异，却不能替代配置初始化，也不能仅凭换板就判定第一块芯片损坏。

### 5 2 通过网口取得独立证据

TwinCAT 的 ESC Access → Memory 可以在 MCU SPI 未打通时读取 ESC 寄存器。早期 0x0140 读两字节显示 0x0C00，低字节 PDI 类型为 0，并非目标 0x80；0x0502 读到 0x1880。这里保留原始字值，不把全部 EEPROM 状态位未经核对就逐位下结论。

这些结果与空白 EEPROM、身份全 FF 相互印证，应先建立有效配置。网络 Working Counter 为 1 也表明，问题不能一开始就笼统判断为整块 LAN9252 完全不工作。

### 5 3 备份和写入的实际操作

先在 Box 1 → EtherCAT → Advanced Settings → ESC Access → E²PROM → Hex Editor 读出原内容，并使用 Write to File 保存写入前备份。聊天截图中的文件为 B板_EEPROM_写入前_20261014.bin，保存在 D 盘的 TwinCAT Project2 目录，资源管理器显示约 1 KB。

随后安装并重载实验 ESI，使用 Download from List，选择 H743-LAN9252-LAB，对应产品号 37458、revision 1，执行 EEPROM 写入。写后上传显示不再是全 FF，配置区和设备字符串已经出现；后续需以硬件重新上电后的实际寄存器为装载依据，不能把电脑编辑区的内容直接当成上电已生效。[R1][R4]

### 5 4 写入后的变化与核对边界

TwinCAT 设备名称由未知 Box 变为 H743-LAN9252-LAB，0x0502 读到 0x0080，0x0140 两字节读到 0x0E80。应区分这两个字节：低字节 0x80 是 PDI 类型，高字节属于相邻配置，不能把整个 0x0E80 当成单字节 PDI 类型。

备份显示约 1 KB，而 ESI 目标有效大小为 2048 字节；这不能据此证明物理 EEPROM 容量，也不能宣称已完整备份全部目标区域。正式归档还应补齐整段回读、散列和配置区校验。EEPROM 写入是必要准备，但后续仍存在 SPI 分段和偶发超时问题，不能把所有故障都归因于 EEPROM。

# 6 SPI 基础通信与 IO 保持问题

### 6 1 用固定寄存器代替只看波形

我们将 BYTE_TEST 作为第一项稳定、可重复的 SPI 验证。它位于 LAN9252 主机寄存器 0x0064，正确值为 0x87654321。只看到时钟或看到 MISO 翻转不够，还要验证命令、地址、dummy、CS 连续性、数据字节序和返回值。

启动时增加一次只读对照诊断 g_lan9252_spi_debug，保留原 EtherCAT_Init 的成功或失败结果，不覆盖原状态、不写 EEPROM、不自动清错。三种方法均读取同一 BYTE_TEST，减少不同寄存器行为造成的干扰。

| 方法 | 线上请求 | 数据位置 |
|---|---|---|
| fast_split | 0B 00 64 00，再传 4 个零字节，分两次 HAL 调用 | rx[4..7] |
| fast_single | 同一 8 字节帧，一次 HAL 调用 | rx[4..7] |
| normal_single | 03 00 64，再传 4 个零字节，共 7 字节 | rx[3..6] |

正确原始数据为 21 43 65 87，按小端组合后为 0x87654321。passed_mask 的 bit0、bit1、bit2 分别对应上述三种读取；三个方法都通过时为 0x07。

### 6 2 整帧成功而分段失败

早期截图中，普通初始化读到的 byte_test 为 0x0ECB8642，驱动报 LAN9252_ERR_BYTE_TEST；只读对照 passed_mask 为 0x06。也就是说，两种整帧方法通过，而分段快读没有通过。这将怀疑范围从“SPI 完全不通”缩小到“跨 HAL 调用的帧连续性”。

H7 SPI 在 HAL 调用结束后的外设关闭与引脚状态处理，与旧平台示例的隐含假设不完全相同。虽然软件 CS 一直保持低电平，如果 SCK 等 IO 在两次调用之间释放或改变，LAN9252 仍可能接收到错误帧边界。

### 6 3 针对性修改和实测结果

SPI1 的 MasterKeepIOState 改为 SPI_MASTER_KEEP_IO_STATE_ENABLE，并同步检查 .ioc 与硬件配置测试，保留 Mode 0、4 MHz、8 位及原有软件片选逻辑。没有通过改采样模式或提高容错条件接受错误 BYTE_TEST。

后续实板截图显示 passed_mask 从 0x06 变为 0x07；BYTE_TEST 为 0x87654321，ID_REV 为 0x92520001，HW_CFG 为 0x08000000，pdi_control 为 0x80，eeprom_status 为 0x0080，初始化返回 READY，驱动错误为 0。[L5]

这一对照有力支持 IO 保持是分段读取异常的原因。但一次启动探测通过只证明当时的访问成功，尚不能证明持续 SSC 服务不会再次遇到错误。

# 7 偶发 INIT 与 PREOP 的定位过程

### 7 1 看似矛盾的状态表现

在 SPI 探测正确后，同一程序有时能进入 PREOP，却不能按请求返回 INIT；有时重新断电或下载后一直停在 INIT，INIT → PREOP 请求在 3000 ms 后超时。TwinCAT 还曾报比较失败：实际 0x0002、目标 0x0001、mask 0x000F。

当时的关键不是继续更换板卡或反复写 EEPROM，而是确认 CPU 运行、驱动服务运行和 ESC 当前状态是否一致。一次成功探测不能覆盖随后数千次访问中的偶发失败。

### 7 2 为什么 MCU 一直运行仍可能无法转换状态

代码采用首错锁存策略。底层发生访问故障后，服务停止继续调用 SSC MainLoop，并将应用通信影子复位为零；CPU 仍可继续执行 while 循环。这是一种故障停止处理策略，并不等于 CPU 死机。

如果故障发生在 SSC 初始化期间，设备可能无法进入 PREOP；如果发生在 PREOP 之后，LAN9252 可保持已有 AL 状态，但 H743 不再处理新的状态请求，于是主站请求返回 INIT 也会失败。这个机制能够解释两个方向的现象，具体故障位置仍需抓取证据。[L5][L6]

### 7 3 对调试画面的两个纠正

ethercat_init_status 保存的是启动函数返回结果，不是实时 AL 状态。初始化为 1 之后运行阶段仍可能发生故障；初始化为 2 时，只读对照后来成功也不会自动把它改为 1。

同样，MCU 运行时 Keil 黄色执行位置和核心寄存器可能保留上次暂停的显示。不能仅凭画面仍在 main 或 PC 看似不变就判定反复复位。hspi1.State 在实时观察中出现 BUSY_TX_RX 也可能只是正在传输，不能单独认定外设锁死。

### 7 4 先加诊断再修复

新增 g_lan9252_first_fault 记录物理地址、上层 ESC 地址、命令、命令头或数据阶段、失败分支、耗时和预算；新增 g_lan9252_hal_fault 记录同次失败的 HAL 状态、错误码、超时参数、寄存器和剩余计数。

两个结构在完整写入字段后最后置 valid=1，并锁住 MCU 启动后的首次相关故障，避免后续错误覆盖现场。valid=0 不能当成一条有效故障记录。诊断阶段不先修改 SPI 参数、扩大超时、清错或重试，使新增证据具有可解释性。

复现时 MCU 连续运行，不在 CS 低电平期间单步；失败后先保存 TwinCAT 错误和两份快照，再决定是否暂停读取，不先复位或重新下载。

# 8 首次故障快照与 HAL Tick 边界修复

### 8 1 实际捕获到的关键数据

| 层次与字段 | 实测值 | 定位意义 |
|---|---|---|
| first_fault.valid | 1 | 首次现场完整有效 |
| address 与 esc_address | 0x0304 与 0x0004 | 读取 CSR_CMD，关联 SSC 初始化的 ESC 请求 |
| command 与 phase | 0x0B 与 2 | 快读数据阶段失败 |
| reason 与 status | 2 与 3 | transport 返回失败，DIRECT_TIMEOUT |
| elapsed_us 与 budget_us | 39 与 1000 | 整次物理访问记录耗时远小于微秒预算 |
| hal_status 与 hal_error | 3 与 0x100 | HAL_TIMEOUT，错误码需结合本次路径解释 |
| HAL elapsed_us | 11 | HAL 回调很快就返回超时 |
| timeout_us 与 timeout_ms | 977 与 1 | 剩余 977 微秒被换算为 HAL 的 1 ms 参数 |

截图中的原始十六进制耗时分别为 0x27、0x0B、0x3D1 和 0x3E8，上表换算为十进制微秒。此次 ethercat_init_status=2，服务最大耗时仍为 0，与初始化中失败而非正常服务后失败一致。

### 8 2 为什么 1 ms 参数会在几微秒后到期

本地 H7 HAL 使用 HAL_GetTick 的整数毫秒差值判断超时，相关判断是 tick 差值大于等于 Timeout。它不保证“传入 1 就至少等待完整 1 ms”。如果调用从当前毫秒末尾开始，几微秒后 Tick 加 1，差值已经达到 1，HAL 就可能报超时。

例如在某一毫秒的第 995 微秒开始等待，下一个 Tick 约 5 微秒后到来。微秒 DWT 计时仍远未达到 1000 微秒，但 HAL 的毫秒条件已经满足。因此，39 微秒的驱动耗时和 HAL_TIMEOUT 并不自相矛盾。这也解释了同一代码随启动时刻不同而偶发失败。[L5]

### 8 3 修正的是换算与保护余量

板级适配器将 HAL 超时参数改为“剩余微秒预算向上取整到毫秒，再加 1 个 Tick”。剩余 1 至 1000 微秒时传入 HAL 的是 2 ms。实现使用商和余数，避免 remaining_us 加 999 可能发生的整数溢出。

```c
remaining_us = timeout_us - elapsed;
timeout_ms = remaining_us / 1000U + 1U;
if (remaining_us % 1000U != 0U) ++timeout_ms;
```

驱动的 1000 微秒结果接受预算和调用前后检查保留；HAL 晚完成仍返回失败，不增加自动重试，不修改 HAL 库或原始 BYTE_TEST 判据。该修正不是硬 1 ms 返回保证，HAL 故障等待仍可能接近 2 ms，加上中断和适配器开销，后续实时性能必须单独评估。

主机模型覆盖 1000 个整数微秒 Tick 起点，同时检查晚完成拒绝、分块共享预算和无重试。实板后续截图中两份故障 valid=0，驱动错误和超时计数为 0，并恢复 PREOP 与在线 CoE；这支持修复有效，但长期稳定性仍需另行记录。

# 9 从 PREOP 到 SAFEOP 和 OP 的主站操作

### 9 1 PREOP 在线对象读取成功

故障修正后，TwinCAT 的 Box 1 → CoE - Online 显示 Online Data，未勾选 Show Offline Data，并能够读取设备名、硬件版本、软件版本及 0x1018 身份。截图中 Vendor ID 为 0x00F0C743，Product Code 为 0x00009252，Revision 为 1，Serial Number 为 1。

这证明邮箱、CoE 和 H743 的对象字典处理已经实际工作。仅有对象列表不一定代表在线读取；本次需要结合 Online Data 标识、实际值及相应运行状态确认。PREOP 阶段仍不以 PDO 计数器增长作为通过条件。

### 9 2 从站 SafeOp 请求被主站状态限制

在 Box 1 的 Online 页点击 Safe-Op，出现“Master state PREOP is insufficient”。这次错误与之前的 SPI 故障不同：从站请求尚受到主站状态限制，应先查看父节点 Device 2 的状态，不能仅在 Box 1 上重复请求。[R1]

随后进入 Device 2 → Online，点击主站 Safe-Op 仍不变化。关键证据是 Cyclic 列发送帧数和 Frames/sec 都为 0，而 Queued 列仍有收发。Queued 是非周期通信，能够读邮箱或寄存器不等于已经具备周期 PDO 通信。[R1]

### 9 3 启动 FreeRun 而不是继续修改固件

TwinCAT 可配置为在同步任务开始发帧前保持 PREOP。此次没有运行 PLC 周期任务，且 FreeRun 周期通信尚未启动，符合“主站一直停在 PREOP”的现象。[R2]

处理顺序是选中 Device 2 → EtherCAT → Advanced Settings → State Machine → Master Settings，将 Startup State 暂设为 SAFEOP，保留 Stay at PRE-OP until Sync Task started，避免通过取消等待条件绕开问题。保持 Config Mode，再执行 TwinCAT → Toggle Free Run State；该命令可在没有 PLC 任务时驱动 I/O 周期通信。[R3]

该命令是开关，不应反复点击。若目标系统此前处于 Run Mode，官方说明要求先 Reload Devices，再使 I/O 驱动进入 FreeRun；这属于可复现操作的条件说明，不是本次已执行的额外步骤。

### 9 4 实际进入 SAFEOP 与 OP

后续截图显示 Box 1 的 Current State 与 Requested State 均为 SAFEOP，InfoData.State=4，WcState=0，错误数为 0。StatusWord 和 CycleCounter 此时为 0，符合本应用在尚未接收有效 OP 输出前保持零影子的设计。

确认 SAFEOP 后，保持功率级禁用和 ControlWord=0，在 Device 2 → Online 请求主站 OP，再查看 Box 1。最终截图显示 OP、State=8、WcState=0、CycleCounter=2127。至此，主站操作与从站固件共同完成首次 OP，不能只用“SPI 修好了”概括最后这一段状态推进。

# 11 最终可复现的逐级操作流程

### 11 1 固件和台架准备

1. 保持电机断开与功率级禁用，确认 PC4 为低，编译宏 ETHERCAT_BRINGUP_ONLY=1。不要为了进入 OP 切换到电机模式。
2. 核对 SPI1 引脚、Mode 0、4 MHz、8 位、软件 CS 和 MasterKeepIOState=ENABLE。确认实际固件包含本次 Tick 边界修正。
3. 用已保存的工程完成 Rebuild，由操作者下载固件。记录实际 HEX 散列；下载过程和调试器设置不等价于板上冷启动测试。
4. MCU 持续运行，检查 BYTE_TEST、ID_REV、HW_CFG、PDI、EEPROM 及初始化结果；保留首故障诊断，不自动清错。

### 11 2 ESI 和 EEPROM 准备

5. 将实验 XML 安装到本机实际 TwinCAT XAE 所用 Config/Io/EtherCAT 目录，重载描述或重启 XAE。常见默认路径为 C:/TwinCAT/3.1/Config/Io/EtherCAT，以本机安装为准。[R4]
6. 对空白板先上传并完整备份 EEPROM，再核对目标设备和候选配置，确认后写入匹配 SII。已写好且核对正常的板不需要每次重写。
7. 写后再次上传回读并核对；完整断开逻辑供电再上电，避免调试器或其他接口反向供电。确认新身份与 PDI=0x80 已装载。

### 11 3 主站按状态推进

8. Config Mode 下扫描正确网卡与从站，保持 DC 关闭；先采用适合首次台架的较宽周期，建议 10 ms，并在主站设置中核实实际周期。当前 OP 截图并未证明其实际数值。
9. INIT 检查身份与 probe；PREOP 检查在线 CoE 0x1018；不只看设备名称或状态按钮是否高亮。
10. 将主站启动目标暂设 SAFEOP，启动 FreeRun，检查 Cyclic 帧数增加且 Frames/sec 大于 0，再验证从站 SAFEOP、State=4、WcState=0。
11. ControlWord 保持 0，从 Device 2 请求主站 OP，再确认 Box 1 实际 OP、State=8、WcState=0、计数器持续变化。若从站被设置了独立 Final State 上限，需先明确核对该限制。

### 11 4 失败时保留现场

12. 保存主站 Current/Requested State、完整错误原文、AL Status 和 AL Status Code，再保存 MCU 驱动错误、超时计数和两份首次快照。不要先复位、重新下载或重写 EEPROM。

遇到访问故障锁存，主站 Clear Error 不能替代 MCU 端显式恢复。先查明原因；正常网线掉线与 SPI transport 故障要分开处理。只有明确开启新一轮实验时才复位或重新初始化，且记录这一步。

# 12 阶段收获与下一步验收

### 12 1 本次调试得到的方法

第一，按层验证比围绕一个表面现象反复试参数有效。MISO 没返回时，要区分电气连接、PDI 上电配置和 SPI 帧；PREOP 超时时，要区分启动成功、持续服务、邮箱处理与主站周期是否运行。

第二，对照实验必须尽量只改变一个因素。三种 BYTE_TEST 读取使用同一寄存器，揭示了分段与整帧差异；首次故障快照保留同一次访问的协议层和 HAL 层数据，才能解释“微秒尚未超预算，HAL 却超时”。

第三，调试器数据需要结合发布方式理解。启动结果不是实时状态，CPU 继续运行不代表 SSC 仍在服务，运行中的黄色执行位置可能是旧显示，HAL 清理后的传输计数为零也不证明传输成功。

第四，主站工具本身也是系统的一部分。只安装 ESI、只进入 PREOP 或只读取 CoE 都不足以完成周期 PDO；需要正确的主站状态、有效周期源和主从两端一致的 PDO 配置。

### 12 2 后续测试应如何开展

| 下一项测试 | 通过条件与记录要求 |
|---|---|
| 零输出稳定性 | 保持 OP 至少 10 分钟，WcState=0，计数持续变化；比较网络与 SPI 错误计数基线和终值 |
| 非零 PDO 回环 | 经确认后按 0、1、2、3 输入控制字，状态字应为 0、1、0、1；用周期 PDO 而非仅 SDO 写入 |
| 重复冷启动 | 多轮真正断电重启，分别记录 probe、PREOP、SAFEOP、OP 和是否出现首故障 |
| 状态往返 | 连续运行下多轮 INIT、PREOP、SAFEOP、OP 往返，无方向性卡死 |

10 月 14 日健康 PREOP 截图曾显示 ethercat_service_max_us=0x119E，即 4510 微秒。它是服务调用耗时上限记录，不是总线周期，也不等同于某次 SPI 直接访问耗时。后续评估 1 ms 时应重新测量，不能依据当前 OP 就承诺 1 ms 实时性。

### 12 3 可直接用于口头汇报的总结

本阶段我先将 F407 参考工程中的最小 SSC 和 LAN9252 访问逻辑移植到 H743，并将电机控制隔离。实板调试中，先解决空白 EEPROM 与设备描述问题，再通过同寄存器的分段和整帧读取对照，修正 H7 的 SPI IO 保持配置。对于偶发 INIT 与 PREOP 卡住的问题，我增加首故障快照，定位到 HAL 毫秒 Tick 边界造成的提前超时，并修正换算。最后根据 TwinCAT 的周期帧计数确认 FreeRun 未启动，补齐主站操作，完成 SAFEOP 和 OP。目前已经打通通信链路，下一阶段重点是稳定性、完整 PDO 回环和重复上电验收，之后再单独设计电机 EtherCAT 联动。
